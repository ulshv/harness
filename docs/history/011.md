## Goal

A short README video: a user asks one question, the agent walks four systems of a believable company, finds what's
stuck between them, proposes a plan, and on "go ahead" fixes it and tells the people who need to know. Evals are
deferred; the testing warehouse of 006 becomes part of the demo world.

## Concepts

- **The agent is configuration.** The same harness image is a generic assistant or a company's ops assistant,
  depending on the prompt file and `MCP_SERVERS`. Compose merges a second file into a service: keys add up.
- **MCP over someone else's API, four times.** Each server is ~80 lines: tools are descriptions plus a call; the
  intelligence is in the prompt and the model.
- **Policies in the prompt, facts in the tools.** Tool descriptions say what a call does; the prompt says what
  counts as a problem and which order wins. Until the prompt said to follow the rules itself, take 1 left the
  overdue hold and the messages "to a human".
- **Pydantic validation context.** `model_validate(data, context={"now": now})` reaches nested models, so one
  `BeforeValidator` turns every seed offset into a time.

## How to verify

```bash
make up:demo
# http://localhost:8080: "Anything stuck across our systems today?", then "Go ahead"
curl -s 'localhost:8130/messages?to=%23purchasing' | jq '.[-1]'       # the agent chased the supplier
curl -s localhost:8100/orders/OUT-5052 | jq .status                  # "reserved"
curl -s localhost:8110/sales-orders/SO-1041 | jq '{status, hold_reason}'
make test && make lint
```

Rehearsal on a throwaway stack with the live model (DeepSeek via RouterAI), a fresh world per take, checked
through `/_state`. "Found" means the first answer names each scenario; the seven checks after "go ahead" are:
S1 `OUT-5052` reserved and `SO-1041` on hold, S2 the kettle listing at 0, S3 an ERP order for `114-7781302` linked
to a reserved warehouse order, S4 a post to purchasing and one to Maria, S5 `OUT-5048` reserved.

| Take | Prompt | Found | After "go ahead" |
|---|---|---|---|
| 1 | first draft | 5/5 (32 tool calls, 86 s) | 3/7: did the "safe" fixes, left the hold and the messages "for a human" |
| 2 | rules apply themselves, the go-ahead covers notifications | 5/5 (97 s) | 7/7, four people notified |
| 3 | same | 5/5 (79 s) | 7/7 |
| ru | same, asked in Russian | 5/5 (114 s), answer in Russian | 7/7, chat posts in English |

Not checked: that nothing changed before the go-ahead (the script didn't compare `/_state` after the first answer;
every first answer ended by asking for approval). After the review the go-ahead wording was narrowed to "the steps
the user approved"; that version hasn't been rehearsed yet.

## Debrief: takeaways

- Review fixes stayed unstaged per substep; the notable ones: the prompt file is read before the MCP wait, receiving
  takes no moves, a new unpaid order is due after the payment terms (not overdue on arrival), naive datetimes are
  refused, listing prices match the ERP, and the seed tests pin "no sixth stuck state".
- Latency in every testing API showed nothing in the UI for parallel calls: `ToolNode` ran all calls of a step and
  `updates` reported them together, after the slowest. Now each call is its own `Send` task
  (`send_tool_calls` in `agent/graph.py`), so results stream as they finish, out of order.
- A fresh `uv lock` in a new project picked a transitive release from the same day (Starlette 1.9.0); pinned back to
  the siblings' 1.8.0.
