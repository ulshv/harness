# 003. `/chat/stream` + `/chat/invoke`, text batching

**Status:** done, awaiting review and commit
**Commit:** —
**Spec:** [specs/003](../specs/003_chat-stream-invoke-batching.md) · **Arch:** [arch/001](../arch/001_chat-request-flow.md) (updated)

## Goal

Cut the SSE overhead of one-frame-per-token, and add a non-streaming route for tests and scripts,
built on the same event pipeline.

## What was added

- `app/api/chat/batching.py`: `batch_text_events(events, window)` with `TEXT_FLUSH_INTERVAL = 0.05`.
- Routes `POST /chat/stream` (SSE, batched) and `POST /chat/invoke` (`{"events": [...]}`). `POST /chat` is removed.
- The `token` event is renamed `text`: after batching it carries a chunk or a whole block of text.
- Event classes get an `Event` suffix: `TextEvent`, `ToolCallEvent`, `ToolResultEvent`. Our `ToolCall` used to share
  its name with LangChain's `ToolCall` (the dicts in `msg.tool_calls`), and `stream.py` builds one from the other.
- Events have `type: Literal[...]` instead of `event: ClassVar`. In SSE it is only the `event:` line, not part of `data`.
- `chat_events(graph, message)` builds the `HumanMessage` itself.
- Tests: `test_batching.py` (windows `0` and `inf`), chat tests moved to both routes, plus 404 on the old route.

## Concepts

- **Async generators as a pipeline**: translate → batch → encode, each stage a generator over the previous one.
- **Flush-on-arrival batching**: a time window checked when a text event arrives, with no timer. The trade-off and
  upgrade path are in the spec.
- **Edge windows as tests**: `0` and `inf` test the logic deterministically, without fake clocks or sleeps.
- **SSE data encoding in FastAPI**: a pydantic model goes through `model_dump_json()` (compact); a `dict` goes
  through `json.dumps` (spaces after `:` and `,`). `raw_data` sends a preformatted string as is.

## How to verify

```bash
make test && make lint          # 21 passed
Q='{"message":"Explain in about 120 words why SSE is good for LLM streaming."}'
curl -sN localhost:8000/chat/stream -H 'content-type: application/json' -d "$Q" | grep -c '^event: text'
# 11 on the live run (≈174 before batching)
curl -s localhost:8000/chat/invoke -H 'content-type: application/json' -d '{"message":"what time is it in UTC?"}' | jq
# {"events": [tool_call, tool_result, one text event with the whole answer]}
curl -s -o /dev/null -w '%{http_code}\n' localhost:8000/chat -d '{}'   # 404
```

Live run on DeepSeek v4.1 flash: 11 text frames, 1.1 KB for the whole stream (6.4 KB before).

## Knobs

| Knob | Where | What you'll see |
|---|---|---|
| `TEXT_FLUSH_INTERVAL` | `api/chat/batching.py` | `0` → one frame per LLM token again (~170); `0.2` → chunky "paragraph" updates |
| `window=` in `invoke` | `api/chat/chat.py` | `0` → `/invoke` returns every LLM token as a separate `text` event |
| `exclude={"type"}` | `api/chat/chat.py` | drop it → `type` reappears in every SSE `data` |

## Gotchas

- `ServerSentEvent(data=<dict>)` is serialized with `json.dumps` (non-compact), while `data=<model>` uses
  `model_dump_json()`. To send a model without some fields compactly, use `raw_data=model.model_dump_json(exclude=...)`.
  (`fastapi/routing.py`, the SSE branch.)

## Questions

1. Why is batching a separate module instead of part of `stream.py`?
   <details><summary>Answer</summary>`stream.py` translates graph semantics into events. Batching is a transport policy about how many frames to send. Keeping them apart lets `/invoke` reuse batching with a different window and keeps both testable without a graph.</details>
2. With `window=0.05`, can two AI messages' texts end up in one `text` event?
   <details><summary>Answer</summary>No. Between two AI messages there's always a non-text event (`tool_call` before the tools run), and every non-text event flushes the buffer first. The final message is flushed at the end of the stream.</details>

## Debrief: takeaways

Opus review of the staged diff. Fixed before commit:

- **The time window had no test.** Windows `0` and `inf` never exercise "counted from the first chunk": an
  idle-reset bug would pass both, and in prod a steady token stream would then never flush. `batching.py` now
  reads `monotonic()` once per text event, and a test patches it with literal ticks.
- **OpenAPI didn't discriminate events.** `type` was optional (it has a default), and the union was a plain
  `anyOf`. Now there's a `Field(discriminator="type")` and `json_schema_serialization_defaults_required`
  (on a small `_Event` base), plus a test on `/openapi.json`.
- **Two comments overclaimed.** "One block per AI message" became "per contiguous run of text", and arch/001
  now credits the ReAct graph, not batching, for keeping AI messages apart.

Documented, not fixed:

- **Text before a tool call waits for the tool-call arguments to finish** (added to the spec's trade-off).
  It's invisible with `current_time` and matters for big-argument tools in step 4.
- **On disconnect, inner generators are closed by the asyncgen finalizer one loop tick later.** Verified:
  closing the outer generator closes the source right after, not with it. This belongs with the deferred
  client-disconnect item from history 002.
