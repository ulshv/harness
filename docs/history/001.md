# 001. First agent: LangGraph + one tool + SSE

**Status:** done, awaiting a live smoke with a real key, review and commit
**Commit:** —

## Goal

`POST /chat` runs a LangGraph agent with one tool on DeepSeek via RouterAI and streams
tokens, tool calls and tool results over SSE; watch it with `curl -N`.

## What was added

- `app/agent.py`: a hand-built ReAct graph (`StateGraph(MessagesState)`: `agent` ⇄ `tools`),
  tool `current_time`, model `ChatOpenAI` pointed at `https://routerai.ru/api/v1`.
- `app/main.py`: `POST /chat` with FastAPI's native `EventSourceResponse`; events `token`, `tool_call`, `tool_result`.
  The graph comes from a cached dependency `get_graph`.
- `tests/test_chat.py`: a fake model scripted with "call the tool, then answer"; checks the SSE event sequence.
- `.env.example` with `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`; compose reads `.env`.
- Fixes from the step 0 review (see `000.md`): loopback-only port, `--reload-dir`, graceful timeout, `.dockerignore`.

## Concepts

- **State + reducer**: `MessagesState` is `{"messages": list}` with the `add_messages` reducer,
  so a node returns only the *new* messages and LangGraph appends them.
- **Nodes and edges**: `agent` calls the LLM, `tools` (`ToolNode`) executes `tool_calls`;
  `tools_condition` is a conditional edge: tool calls → `tools`, otherwise → `END`. `tools → agent` closes the loop.
- **`bind_tools`** doesn't run anything: it attaches tool JSON schemas to the request; the model only *asks* for a call.
- **Stream modes**: `messages` = LLM tokens as they arrive, `updates` = each node's finished output.
  Several modes at once give `(mode, data)` tuples.
- **SSE in FastAPI ≥ 0.135**: `response_class=EventSourceResponse` + `yield ServerSentEvent(...)`;
  keep-alive pings every 15 s, `Cache-Control: no-cache` and `X-Accel-Buffering: no` come for free.
- **OpenAI-compatible providers**: RouterAI speaks the Chat Completions dialect, so `ChatOpenAI(base_url=...)` is enough.

## How to verify

```bash
cp .env.example .env            # put the key into LLM_API_KEY
make up
curl -N localhost:8000/chat -H 'content-type: application/json' -d '{"message":"what time is it in UTC?"}'
# event: tool_call    data: {"name":"current_time","args":{}}
# event: tool_result  data: {"name":"current_time","content":"2026-..."}
# event: token        data: {"text":"It"} ... many small token events
curl -N localhost:8000/chat -H 'content-type: application/json' -d '{"message":"tell a one-line joke"}'
# only token events: the model decided no tool was needed
make test
```

Also: `localhost:8000/docs` lists `POST /chat`.

## Knobs

| Knob | Where | What you'll see |
|---|---|---|
| `SYSTEM_PROMPT` | `app/agent.py` | tone/length of answers; "never use tools" → no `tool_call` events |
| `LLM_MODEL` | `.env` (restart: `docker compose up -d --force-recreate`) | other DeepSeek (`deepseek/deepseek-v4-pro`) or any model from the list |
| `temperature=` in `ChatOpenAI(...)` | `app/agent.py` | 0 → near-identical answers on repeat |
| `TOOLS` list | `app/agent.py` | remove `current_time` → the model guesses the time or says it can't know |
| `recursion_limit` | `graph.astream(..., config={"recursion_limit": 3})` | `GraphRecursionError` when the agent loops through tools too long |
| `stream_mode` | `app/main.py` | drop `"messages"` → the answer arrives in one piece at the end |

## Gotchas

- LangGraph 1.2 has an experimental `stream_events(version="v3")` with typed per-channel streams;
  classic `astream(stream_mode="messages")` still yields `(AIMessageChunk, metadata)` and also emits `ToolMessage`s.
- FastAPI got native SSE (`fastapi.sse`) in 0.135; no `sse-starlette` needed.
- `ChatOpenAI` ignores OpenRouter-style `reasoning` fields, so DeepSeek's reasoning isn't streamed (only the answer).

## Questions

1. Why does `agent` return `{"messages": [reply]}` and not the whole list with the reply appended?
   <details><summary>Answer</summary>The `add_messages` reducer merges the node's output into state: it appends new messages (and replaces ones with the same id). Returning the whole list would still work thanks to id dedup, but it's noise and breaks once messages lack ids.</details>
2. In the test the model never really "decides" anything. What exactly does the test prove then?
   <details><summary>Answer</summary>The wiring: the graph routes a tool call to `ToolNode`, the tool result goes back to the model, and our endpoint maps every step to the right SSE event. The model's judgment is checked by the live smoke (and later by evals).</details>
