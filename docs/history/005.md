# 005. `reasoning` event

**Status:** done, reviewed
**Commit:** —
**Spec:** [specs/005](../specs/005_reasoning-event.md) · **Arch:** [arch/001](../arch/001_chat-request-flow.md) (updated)

## Goal

Stop the ~11 s of silence before DeepSeek's first token: stream its reasoning as its own event, batched
like text, so the frontend can show it in a spoiler.

## What was added

- `agent/llm.py`: `ChatDeepSeek` (`langchain-deepseek==1.1.1`) instead of `ChatOpenAI`. The direct
  `langchain-openai` dependency was dropped; it's transitive now.
- `ReasoningEvent` (`type: "reasoning"`, `{"text"}`) in the `ChatEvent` union.
- `stream.py`: `_from_tokens` reads `msg.content_blocks` and maps block type to event via `_BY_BLOCK`.
- `batching.py`: `batch_text_events` → `batch_events`, `TEXT_FLUSH_INTERVAL` → `FLUSH_INTERVAL`. It merges runs of the same kind (text or reasoning),
  and a change of kind flushes.
- Tests: `StreamingFakeModel(reasoning=[...])`, translator block tests, batching by kind, reasoning in
  stream and `/invoke`, OpenAPI mapping, a mixed text+reasoning chunk, a signature-only reasoning block.
  45 tests total.

## Concepts

- **Provider packages vs `ChatOpenAI`**: `ChatOpenAI` handles the official OpenAI schema only and drops
  `reasoning` / `reasoning_content`. A provider subclass of `BaseChatOpenAI` reuses everything (openai SDK,
  error wrappers) and adds the extra fields.
- **`content_blocks`**: langchain-core's standard, provider-neutral view of a message. Text, reasoning and
  tool-call chunks become typed blocks, so the translator never reads provider-specific kwargs.
- **Batching by kind**: the buffer holds one event, and a different kind flushes it. That's the same rule as
  "a non-text event flushes", generalized.

## Gotchas

- `ChatOpenAI` 1.7.2 still drops reasoning by design (its module docstring says so). RouterAI sends it as
  `delta.reasoning` (OpenRouter style), and `ChatDeepSeek` parses that too.
- `langchain-openrouter` 0.2.9 needs the `openrouter` SDK, which pins `pydantic<2.13`; unusable with 2.14.
- Usage comes from **RouterAI itself**: it puts usage in the last chunk with no flag. `_should_stream_usage()` is
  `False` for both `ChatOpenAI` and `ChatDeepSeek` with a custom `base_url`, so `stream_options` isn't sent.
  `usage_metadata` includes `output_token_details.reasoning`. (Spec 004's non-goal implied usage was
  unavailable; with RouterAI it never was.)
- **Reasoning isn't echoed back inside the ReAct loop**: the re-sent tool-calling `AIMessage` loses its
  `reasoning_content` (`ChatDeepSeek` 1.1.1 never sends it), and the follow-up answer comes without reasoning.
  DeepSeek's own rules ([thinking mode](https://api-docs.deepseek.com/guides/thinking_mode)): **across turns**
  it's ignored (no context bloat, no need to send); **within a turn with `tools`** it must be passed back,
  otherwise the native API returns 400. RouterAI tolerates the omission. Left as is on purpose: a fix means
  overriding message serialization; revisit at step 4 or on a provider switch (roadmap backlog).
- **Provider variance**: one of three early live runs came back with no reasoning and ~7 s to the first frame,
  served by the same process and code as the later runs that had reasoning. Five raw API calls right after
  all streamed reasoning (16–119 chunks, upstream `DeepSeek`, ~1.5 s). Treat reasoning as optional; the
  client must not wait for it.

## Questions

1. Why read `content_blocks` instead of `additional_kwargs["reasoning_content"]`?
   <details><summary>Answer</summary>`reasoning_content` is one provider family's convention (DeepSeek, Ollama, xAI, Groq). Anthropic puts thinking in content blocks, OpenAI's Responses API in reasoning items. `content_blocks` normalizes them all to `{"type": "reasoning"}`, so the translator doesn't change when the provider does.</details>
2. Why does the reasoning → text switch flush the buffer even if the window hasn't passed?
   <details><summary>Answer</summary>The buffer holds one event of one kind. Appending text to reasoning would mislabel it, and holding the text back until the window passes would delay the first answer frame. A kind change is a boundary, just like a tool call.</details>

## Debrief: takeaways

Opus review of the staged diff. It also ran one live ReAct loop through RouterAI: reasoning ×2 → tool_call →
tool_result → text → done. Fixed after review:

- **`KeyError` on a reasoning block without text.** `reasoning` is `NotRequired` in `ReasoningContentBlock`.
  Signature-only blocks (Bedrock, OpenAI Responses with an empty summary) would have crashed the translator
  into `error: internal` mid-stream. It's now read with `block.get("reasoning", "")`, with a test case.
- **Usage was credited to the wrong thing** in ROADMAP and in this file's gotchas: RouterAI sends it, not `ChatDeepSeek`.
- **The spec's non-goal mis-scoped reasoning echo** as a memory/multi-turn concern. It already happens inside
  one ReAct turn (rewritten, plus a backlog item).
- **Stale comments**: "text" became "text/reasoning" in `chat.py`, `stream.py` and the batching constant's comment.
- **Spec said `api_base=`**, the code passes the `base_url=` alias.
- **Added test**: a chunk with both reasoning and text gives reasoning first.

After review, at the user's call: `TEXT_FLUSH_INTERVAL` → `FLUSH_INTERVAL`, since it now governs reasoning runs too.
