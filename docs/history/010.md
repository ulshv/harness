activity block (reasoning, tool calls) and Markdown, 010.3 threads and scrolling.

## 010.1. Text stream in the browser

### What was added

- `services/webapp`: Vite 8.3 + React 19.3 + TypeScript 6.0 + Tailwind 4.3, layered as `api/` → `chat/` →
  `containers/` / `components/` → `pages/`.
- `streamChat()`: SSE over a `fetch` POST, parsed by `eventsource-parser`; event types generated from harness's
  OpenAPI (`make api-types`).
- `chat/turn.ts`: `applyEvent` folds events into a turn (text only for now), `closeTurn` ends a turn that got no
  `done`/`error`. Send is disabled while the last turn streams.
- Design tokens in `index.css` with the default palette reset; dark mode from `prefers-color-scheme`.
- compose service `webapp` on `127.0.0.1:8080`, Vite proxies `/api/*` to harness; `make test` / `make lint`
  include the webapp (10 tests; oxlint, Prettier, `tsc -b`).

### Concepts

- **`EventSource` can't POST**, so the stream is read by hand: `response.body` → `TextDecoderStream` →
  `EventSourceParserStream`. A bonus: `fetch` never reconnects, while an `EventSource` would restart the agent.
- **The SSE event name is the discriminator.** harness keeps `type` out of `data`; the client puts it back, and
  the generated union narrows on it.
- **A dev proxy instead of CORS.** The browser sees one origin; prod will do the same with a reverse proxy.
- **Functional state updates in a long `async` loop**: the closure holds the render it started in, so
  `setExchanges(all => …)` instead of reading `exchanges`.
- **Tailwind 4 is configured in CSS.** `@theme` variables become utilities; `--color-*: initial` removes the
  built-in palette, so only the tokens exist.

### How to verify

```bash
npm ci --prefix services/webapp    # once, for make test / make lint on the host
make test && make lint
make up                            # restart it: the webapp service is new
open http://localhost:8080
```

1. "Can we fully reserve order 1003? Just check." → "Working…", then the answer streams in; Send stays disabled
   until it ends. Type the next question meanwhile: it waits in the box.
2. Stop harness (`docker compose stop harness`), send → "Request failed (502)", Send comes back.
3. Change `--color-accent` in `src/index.css` → the button changes color without a reload.

Smoke run before review, against `make up`'s harness with the webapp image in a throwaway container on the same
network:

- SSE through the Vite proxy arrives frame by frame (`text` came 1.3 s after `tool_result`), not buffered.
- Headless Chrome, order 1003: 14 s of "Working…" (reasoning and tools aren't shown yet), then the answer; Send
  enabled on `done` at 18.1 s. The interim "I'll check order 1003…" and the answer run together (`…changes.No —`),
  and Markdown shows as raw pipes: both are 010.2.
- A webapp pointed at a dead harness: the proxy answers 502, the reply says "Request failed (502)".
- `docker cp` of an edited `index.css` into the container → `[vite] hmr update /src/index.css`.
- Light and dark themes both read well.

### Debrief: takeaways

Opus review of the staged diff. Fixed after review:

- **A harness that died mid-stream locked the composer forever.** Vite's proxy pipes the response and only answers
  502 before the first byte; after it, an upstream death never ends the browser's response. Reproduced against
  our `vite.config.ts` (an upstream that sends one frame and drops the socket: still hanging after 5 s); now
  `configure` destroys the response when the upstream one closes incomplete, and the stream ends in ~320 ms →
  "Connection lost". A client-side idle watchdog went to the backlog.
- **`streamChat` didn't cancel its reader on an early exit** (a parse error, a consumer's `break`), leaving the
  connection and the agent run open: `finally { reader.cancel() }`.
- **Unexpected errors hid behind "Connection lost"**: non-`HttpError`s go to `console.error` too.
- **oxlint warnings didn't fail `make lint`** (every default rule is a warning): `--deny-warnings`.
- `color-scheme: light dark`, so scrollbars and form controls follow the dark theme; `wrap-break-word` on
  messages; the proxy matches `/api/`, not `/apiary`; tests for tool events and a UTF-8 character split across
  chunks (10 tests); comment and doc fixes.

Found along the way:

- TypeScript 6 turns `strict` on by default, which is why the `create-vite` tsconfig doesn't mention it.
- `create-vite` 9 ships oxlint, not ESLint.
- `openapi-typescript` 7.13 still declares `typescript@^5` as a peer, so it runs through `npx` instead of
  living in `devDependencies`.
- `ReadableStream` async iteration isn't in every browser yet; `streamChat` uses a reader loop.

## 010.2. Activity block and Markdown

### What was added

- The turn is a list of parts (`reasoning`, `text`, `tool`); `applyEvent` merges fragments and pairs tool
  results with their calls by id. `splitTurn` derives the answer (text after the last step) on every render;
  `describeActivity` writes the one-line summary.
- `Activity`: live (open, 6 lines tall, follows the newest step) while the agent works, folded into
  `Reasoning · 3 tool calls · 1 failed` once the answer starts; a click opens it. Tool steps show a spinner, then
  ✓ / ✗, and the result as pretty JSON behind `<details>`.
- The answer renders as Markdown (`react-markdown` + `remark-gfm`), styled by `@tailwindcss/typography` with its
  colors pointed at our tokens.
- `TailScroll`, `Spinner`, `Markdown` components. 19 tests.

### Concepts

- **Derive, don't store.** Whether text is the answer depends on what comes after it, so it's computed from the
  parts each render; there's no "answer started" flag to get out of sync.
- **`ResizeObserver` for "follow the bottom".** It fires on any growth of the content (new steps, a step getting
  longer), not only on React renders; the scroll direction decides whether the user let go.
- **`lh` units**: `max-height: 6lh` is six lines of the element's own line height.
- **Markdown from a model is untrusted input.** react-markdown builds React elements, so raw HTML shows as text;
  images become their alt text, because a fetched image URL is a way to send data out.

### How to verify

```bash
make test && make lint
open http://localhost:8080      # make up rebuilds webapp itself: package.json changed
```

1. "Can we fully reserve order 1003? Just check. Answer with a table." → the activity block fills (reasoning,
   `wms_get_order`, two `wms_get_stock`), folds to `Reasoning · 3 tool calls`, the answer is a real table with
   bold text. Click the summary: the steps; click a tool: its JSON.
2. "Check stock of every product one by one and give me a short table." → the live block overflows and follows
   the newest step; scroll it up while it runs and it stops following. `SCN-01` comes back ✗.
3. Switch the OS theme: Markdown, the block and the tool marks follow.

Smoke run before review (headless Chrome against `make up`):

- Order 1003: live block at 2.0 s (`Reasoning · 1 tool call`), `3 tool calls` at 3.5 s, folded with the answer at
  5.0 s; `done` at 6.0 s. One `<table>`, two `<strong>` in the answer.
- Every product: the live block overflowed and stayed pinned (`scrollTop + clientHeight = scrollHeight`: 217 + 119
  = 336, then 277 + 119 = 396); summary `Reasoning · 10 tool calls · 2 failed`.
- The "honest jump", as designed: "Found 8 products" showed as the answer at 5.1 s, then 8 `get_stock` calls
  arrived, the block reopened live and the text moved into it as an interim note.
- Light and dark both read well; the tool JSON is legible in both.

| `Step` | `containers/Activity.tsx` | how reasoning, interim notes and tools look |

### Debrief: takeaways

Opus review of the staged diff. Fixed after review:

- **An unknown event type blanked the page.** Without a `default`, `applyEvent` returned `undefined` for a type
  outside the union, and `Reply` crashed on `turn.parts`; a harness newer than the webapp (the todo list in step
  4) would hit it. Now unknown types are skipped, and `event satisfies never` keeps the compile-time check that
  every known type is handled.
- **`TailScroll` let go on its own during bursts** (reproduced in headless Chrome: several events in one frame →
  unpinned, 4 runs of 4). Our own `scrollTop` assignment fires `scroll` a frame later; content that grew meanwhile
  looked like "the user scrolled up". The pin now changes only on an upward scroll: 0 unpins under the same
  burst, a real 60 px scroll-up still lets go.
- **A tool without a result spun forever** after the turn ended (an error or a dropped stream between call and
  result): it shows `–` once the block isn't live.
- **Markdown**: images render as alt text (a prompt-injected image URL is an exfiltration channel), links open
  in a new tab, wide tables scroll in their own box, long tokens wrap (010.1's `wrap-break-word` was lost). The
  comment and docs claimed react-markdown "drops" raw HTML; 10.1 shows it as text.
- `Reply` is memoized, so a token re-parses only the streaming answer, not every answer in the chat.
- A whitespace-only text part no longer starts an answer; tests for that, a repeated tool id, an unknown event,
  and an interim note in the measured run (19 tests).
- Smaller: `aria-expanded` and hidden glyphs on the toggle, `role="img"` on the spinner, a chevron on tool rows
  (a flex `<summary>` loses the native marker), `TailScroll` can't have its `ref`/`onScroll` overridden, code
  blocks and bullets visible in light mode, Tailwind no longer scans test files (`.order-1003` was in the CSS).

Kept as is: opening a tool's result in the **live** block scrolls it to the bottom while pinned. The block is
live only while the agent works; reading results is for the folded block.

## 010.3. Conversations and a list that follows the stream

### What was added

- One `thread_id` per conversation (`crypto.randomUUID()`), sent with every message: follow-ups have context.
- "New chat": aborts the running request, clears the list, takes a fresh thread id.
- The message list follows the streaming answer (`TailScroll`, the same component as the live block).
- `Button` got a `quiet` variant (a variants table, not a boolean prop per look).

### Concepts

- **The thread id is the client's to choose.** harness accepts any `[A-Za-z0-9_-]{1,64}` and keeps the history
  under it (history 008); the webapp only has to send the same id back.
- **`AbortController` reaches the agent.** Aborting the fetch closes the connection; the dev proxy closes the
  upstream, harness's SSE generator gets cancelled, and the run stops instead of spending tokens for nobody.
- **Late updates from an aborted loop are harmless by construction**: they look up their exchange by id, and it's
  gone from the list.

### How to verify

1. "Can we fully reserve order 1003? Just check." → then "Which product is short?" → answered from the thread:
   the activity block says only `Reasoning`, no tool calls.
2. Ask something long; while it streams, scroll the page up: it stays where you are. Scroll back down: it follows.
3. Ask "Check stock of every product one by one"; press "New chat" mid-stream → the list is empty, Send works.
   Ask "Which product is short?" → the agent has no idea: new thread.

Smoke run before review (headless Chrome against `make up`, 4 requests):

- Order 1003, then the follow-up: same `thread_id`; the follow-up's activity is `Reasoning` only, the answer
  names TAPE-48 short by 5.
- While both answers streamed, the list overflowed and stayed at the bottom (largest gap from the bottom: 0 px).
- "New chat" 2.5 s into a run (`Reasoning · 1 tool call`): 0 messages left, Send enabled, no traceback in
  harness. That the run really stops was checked in review: a request cut after 4 s left no AI message in its
  thread (a follow-up on the same thread answered both questions).
- The next question went out with a new `thread_id` (requests by thread: `0,0,0,1`); the agent said it had no
  prior context.

### Debrief: takeaways (010.3)

Opus review of the unstaged 010.3 diff; the abort paths (during `fetch`, during `reader.read()`, after a normal
end, late updates after "New chat") were all checked and are correct. Fixed after review:

- **"New chat" didn't re-pin the list** if you had scrolled up: clearing the content clamps `scrollTop` to 0
  without a scroll event, so the next answer didn't follow. `TailScroll` now re-pins whenever the content fits.
- **The `py-1` override on the "New chat" button did nothing**: Tailwind orders utilities by its own rules, not
  by the class string, so the base `py-2` won. Size moved into the `Button` variant table.
- "New chat" is disabled on an empty chat and puts the cursor back in the composer (the composer is keyed by
  thread, so it remounts with `autoFocus` and an empty draft).
- Tests: `thread_id` and the signal reach `fetch`; an abort mid-stream ends with the `AbortError`, not the
  rejected `reader.cancel()` from `finally` (20 tests).

Recorded, not fixed:

- **A lost turn stays in its thread.** After "Connection lost" (a restart, a dropped connection) the composer
  re-enables on the same `thread_id`; harness kept the question but no answer, so the next answer covers both. If
  the cut fell between a tool call and its result, the thread breaks (the "Interrupted runs" backlog item, now
  reachable from the UI). "New chat" is the way out.
- `crypto.randomUUID` exists only in secure contexts (https or localhost); see the backlog.


## 010.4. Thinking folds into a step

A quick tweak: raw reasoning made the live block a wall of italics, and the tool calls drowned in it.

### What was added

- Each reasoning part is one step, like a tool call: `Thinking…` with a spinner while it's the newest step of a
  live block, `✓ Thinking` once anything follows it. A click opens the text.
- `Disclosure`: the `<details>` row with its own chevron, shared by the tool result and the thoughts.
- testing-wms answers after a random 0.1–0.5 s (`LATENCY_SECONDS`, an HTTP middleware): an in-memory store
  replied in a millisecond, so the spinners flashed by and parallel results always came back in order.

### Concepts

- **"Done" is derived, not streamed.** harness sends no "reasoning ended" event; a reasoning part is finished
  when it's no longer the last part, or the block stops being live (the answer started, the turn ended).
- **Latency belongs to the API, not the MCP adapter.** A real system is slow in its backend (database, network),
  so every client sees it: curl, the MCP server, future direct tools. `asyncio.sleep` yields the loop, so
  concurrent requests overlap instead of queueing; tests build the app without latency.

### How to verify

"Can we fully reserve order 1003? Just check." → while the agent works, the live block shows one-line steps:
`✓ wms_get_order(…)`, `✓ Thinking`, …, the newest `Thinking…` spinning. Once folded, open the block and click
`✓ Thinking`: the thought appears in muted italics.

Smoke run (headless Chrome against compose): the live block went `Thinking…` → `✓ Thinking` as the stock calls
arrived; the last `Thinking…` turned ✓ when the answer started; a click on it showed "Check stock for both SKUs."

Latency: `curl -w '%{time_total}\n' localhost:8100/stock/TAPE-48` a few times → 0.23–0.47 s; five parallel
`/orders/1003` requests finished together in 0.5 s, not 2.5 s.
